## 3. BP-02 (P1) — requested pair bound at quote acceptance and before every signature

### Hazard (re-derived from pre-fix source)

`git show b3f9b2b:ios/Bobby/Sources/BaseSwap.swift` — pre-fix `validateQuote` signature was
`validateQuote(_:inputAmount:slippagePct:wallet:now:)` (~:121): it received amount, slippage and
wallet but **no requested tokens**. It verified the response was *an* allow-listed USDC/stock pair
(`symbols.contains("USDC") && symbols.count == 2`, pinned via `validateToken`), so a fully
consistent, fully allow-listed response for a DIFFERENT stock passed while the form's receive label
(`BaseSwapView` `tokenOut`, computed from local picker state) showed the user's selection.

### Fix

- `BaseSwap.swift:128-142` — `validateQuote` now takes `requestedTokenIn`/`requestedTokenOut` and
  requires symbol equality (139-140) AND pinned-address equality (141-142) for both legs.
- `BaseSwap.swift:173-181` — issuer reference required: `stockReference` non-nil, symbol match,
  `issuerPaused == false`, `transferPaused == false`, `usable == true` and
  `status ∈ {"fresh","market-closed"}` (1f8bcd8).
- `BaseSwap.swift:321-330` — `decimalMatchesWord` compares normalized hex digit strings
  (drop leading `0` chars on both sides) — exact integer equality, padding-insensitive (a55e009).
- Call sites: `BaseSwapView.swift:331` (acceptance), `:347` (pre-approval), `:373` (pre-swap) all
  re-run `validateQuote`; `:348` `validateApproval`, `:374` `validateSwap`.
- `BaseSwapView.swift:315` freezes `tokenIn/tokenOut/amount/slippage` into locals at request time;
  `:328` re-checks them after the network round-trip ("selection changed while quoting");
  `:77-86` `onChange` on side/stock/amount/slippage/wallet/eligibility → `resetQuote()`;
  `:357` `guard wallet.address == address` after the approval ("wallet changed after the approval").

### My attacks (test files are MINE, under /tmp/kimi-k3-ios/, not the repo's)

Package `/tmp/kimi-k3-ios/attack-fixed` = byte-exact pinned `BaseSwap.swift` +
`RPCCorrelator.swift` (sha256 `11aa6688…` / `f315f949…`, matching §0) + transport stubs +
`Tests/BobbyTests/K3AdversarialTests.swift` (mine). Package `/tmp/kimi-k3-ios/attack-prefix` =
pre-fix `BaseSwap.swift` from `b3f9b2b` (sha256 `9aeff433…`) + my demonstration test.

`stockReference` key → missing → refused. Undamaged payload round-trips and validates. PASSED.

**A7. Mutability of the requested pair (BaseSwapView)** — the pair passed at acceptance is an

the sequence "user moves the picker between response arrival and validation" throws
`selection changed while quoting`. At sign time the guards deliberately re-read live state
(`:347/:373`) — safe because any live-state change also fires `onChange → resetQuote()`
(`:77-86`, clearing the quote and its buttons when not busy) and the whole form is
`.disabled(phase.busy)` while signing (`:214`, wallet card `:132`). A wallet switch mid-sign
additionally kills the pending RPC (BP-05, below) and is re-checked at `:357` and by
recipient/calldata binding (`BaseSwap.swift:186,247`). All paths fail closed.

BP-02 pair binding is present at all three gates, compares pinned addresses, the requested values

## 4. BP-05 (P2) — wallet responses correlated with the pending JSON-RPC request

### Hazard (re-derived from pre-fix source)

`git show b3f9b2b:ios/Bobby/Sources/WalletBridge.swift:275-277` — pre-fix subscriber:

```swift
AppKit.instance.sessionResponsePublisher
    .receive(on: DispatchQueue.main)
    .sink { [weak self] response in self?.finishRPC(response.result) }
```

`id`, `topic`, `chainId` were discarded; only `result` was forwarded. The UUID guarded the timeout
task, not the response, so the next response of ANY origin completed whichever continuation was
pending.

### Fix

- `RPCCorrelator.swift:23-30` — `check(responseID:responseTopic:responseChain:pending:)` requires
  non-nil pending, non-nil id, exact id equality; topic/chain checked when the SDK supplies them.
- `RPCCorrelator.swift:33-39` — `resultLooksValid` binds result shape to method:
  `personal_sign` = `0x`+130 hex, `eth_sendTransaction` = `0x`+64 hex, everything else rejected.
- `WalletBridge.swift:279-288` — subscriber now forwards `response.id`, `response.topic`,
  `response.chainId` into `finishRPC`, which correlates BEFORE touching the continuation.
- `WalletBridge.swift:392-418` — the bridge builds the `Request` itself and stores
  `PendingRPC(id:topic:chain:method:account:)`; single in-flight (`requestInFlight` at :394);
  120 s timeout guarded by `pendingRPCID`.
- `WalletBridge.swift:420-443` — `finishRPC`: on `.unrelated` it logs and returns (continuation
  untouched); on accept it nils `pendingRPC`/`pendingRPCID`/`pendingRequest` BEFORE resuming and
  applies the method-shape check; `:445-451` `failRPC` likewise nils before resuming.
- `WalletBridge.swift:302-318` — `refreshConnection` fails pending work with `.sessionReplaced`
  when the account changed or the pending topic is no longer among live sessions; wired to
  `sessionsPublisher`, `sessionSettlePublisher`, `sessionDeletePublisher` (:267-278);
  `disconnect()` fails pending first (:321).

### My attacks (same attack-fixed package; correlator run in-process, bridge by construction)

**B1. Accepted exactly once; duplicate/late cannot complete or double-resume.**
Correlator: response after completion (`pending: nil`) → `unrelated("no request pending")`;
late response carrying the previous request's id while a newer one is pending →
`unrelated("id … is not the pending …")`. Double-resume is impossible BY CONSTRUCTION, not just
unlikely: the continuation is reachable only through the stored property `pendingRPC`; both
`finishRPC` (:430-432) and `failRPC` (:447-449) clear it (and `pendingRequest`) BEFORE calling
`resume`, both early-return when it is nil, and every path runs on `@MainActor`, so no second event
can observe a non-nil continuation after the first resume. Swift `CheckedContinuation` traps on
double-resume; the design makes that trap unreachable. The 120 s timeout task is guarded by
`pendingRPCID == id` (:414) so a stale timeout cannot kill a newer request either.

**B2. Wrong topic / wrong chain / id-less / different-id.** Correlator tests (mine):
`topic-B`, case-variant `Topic-A` → topic mismatch; `eip155:84532`, `eip155:845`, `eip155:1`,
trailing-space, leading-space, uppercase `EIP155`, newline-suffixed chains → chain mismatch;
nil topic does not excuse a wrong chain and vice versa; id-less → refused; ids `right(1700)`,
`right(1702)`, padded/case/newline variants, empty string → refused. PASSED.

**B3. Shape bound to method, not only id.** Tx hash (`0x`+64) for `personal_sign` → refused;
signature (`0x`+130) for `eth_sendTransaction` → refused; 129/131-length sigs, `0X` prefix,
non-hex alphabet, empty, missing `0x`, trailing newline → refused; `eth_signTypedData`/`eth_sign`
results refused outright (default branch); uppercase hex accepted (legitimate). PASSED.
Note: `finishRPC` applies `resultLooksValid` BEFORE resuming with a value
(`WalletBridge.swift:435-439`), and `sendTransaction`/`ensureSession` re-check the shape after
the await (:354, :383) — three layers.

**B4. Disconnect / account change / session replacement while pending.** `refreshConnection`
(:306-312) fails pending work with `.sessionReplaced` the moment the address differs from
`pending.account` or the topic leaves the session set; it is invoked by all three session
publishers and by `handleDeepLink`. `disconnect()` fails pending first (:321). Backstop: the 120 s
timeout. Pending work FAILS PROMPTLY; it cannot hang or be completed later (once failed, the
continuation slot is nil — B1).

**B5. Two requests in flight with swapped responses.** Impossible by construction:
`request()` throws `.requestInFlight` when `pendingRPC != nil` (:394), so approval and swap are
strictly sequential (the view also disables its buttons while `phase.busy`). My test
`testK3IdOfADifferentPendingRequestIsRejected` covers the adjacent case: a late response to the
PREVIOUS request (e.g. approval `right(1700)`) arriving while the swap (`right(1701)`) is pending
lands on no continuation.

**B6. Receipt independence from the bridge.** The swap flow never trusts the bridge's "success":
`BaseSwapView.swift:376-381` uses the returned hash only as INPUT to
`BaseSwapAPI.waitForSuccessfulReceipt` (`BaseSwap.swift:439-464`), which polls
`eth_getTransactionReceipt` directly against `https://mainnet.base.org` and requires on-chain
`status == "0x1"`, then `recordReceipt` (`:466-493`) posts the hash to Bobby's receipt endpoint and
requires `ok == true`. Only then does the UI show `.confirmed`. A forged bridge response with a
fabricated but well-shaped hash yields no receipt → `.pendingTimeout`/`.reverted` → error phase.
(Static code-path evidence — ground rules forbid chain calls; both endpoints are plain HTTPS reads
of public RPC/API, keyed by the hash, not by bridge state.)

```
$ cd /tmp/kimi-k3-ios/attack-fixed && swift test
Test Suite 'K3BP05AdversarialTests' passed — Executed 3 tests, with 0 failures
```

Plus the repo's own 6 `RPCCorrelatorTests` passing on the iOS simulator (§2) and in the isolated
package (§1), and the full app compiling against the real Reown SDK at the simulator tier.

### Verdict

Correlation is by JSON-RPC id (exact, non-nil), topic and chain when supplied; result shape is
bound to method at three layers; single-in-flight plus clear-before-resume makes duplicate, late,
foreign and double-resume completion unreachable by construction; session/account/disconnect
events fail pending work promptly; confirmation is independent of the bridge via direct receipt
polling. **CLOSED.**
