## BP-02 (P1) — requested pair must be bound at quote acceptance and before every signature

Hazard (pre-fix, `BaseSwap.swift` `validateQuote` ~:121; call sites `BaseSwapView.swift`
~:310/319/335/345/360): validation received amount, slippage and wallet but NOT the requested
tokens. It checked the response was *an* allow-listed USDC/stock pair while the form's receive
label used the *locally selected* tokenOut. A response for a different allow-listed stock (correct
amount/recipient/router) would be signed while the user believes they are buying another stock.
Second arm: a wallet change after approval was not re-checked before the swap signature.

Attack:
- Quote for GOOGLc when the request was for AAPLc (same amount, recipient, router, spender). Must
  be refused at acceptance AND again immediately before approval AND before the swap.
- Same symbol, different pinned address (look-alike token). Must be refused — the guard must
  compare the pinned address, not the symbol string.
- Change side (buy↔sell), amount, slippage, or wallet between quote acceptance and signing. Each
  must invalidate the quote; the wallet change AFTER approval is the important one.
- ABI amounts (`a55e009` fixed a false rejection on leading-zero nibbles): confirm exact integer
  equality still holds and the normalisation cannot make two DIFFERENT amounts compare equal
  (`0x0a` vs `0xa0`, values with/without leading zeros, empty string, non-hex, > uint256).
- Issuer reference (`1f8bcd8`): missing `usable`, `usable:false`, unknown status, `stale`,
  `paused` must each fail closed; only `fresh` and `market_closed` with `usable:true` and unpaused
  pass. Compare field names and enum strings against the server's `evaluateStockReference` /
  `StockReferenceStatus` in `/tmp/kimi-k3-ios/server-base-swap.ts` — a name drift that makes the
  client skip the check is a reopen.
- Read `BaseSwapView.swift`: is the pair passed from an IMMUTABLE value captured at quote request
  time, or re-read from mutable view state at validation time? If mutable, show a sequence where
  the user changes the picker between response arrival and validation.

## BP-05 (P2) — wallet responses correlated with the pending JSON-RPC request

Hazard (pre-fix, `WalletBridge.swift` ~:275/382/405): the Reown/WalletConnect subscriber discarded
`id`, `topic`, `chainId` and forwarded only `result`; the app's UUID guarded the timeout task, not
the RPC id, so the NEXT response completed WHICHEVER continuation was pending — a late response
after a timeout, a duplicate, a wrong-topic/wrong-chain response, an id-less response, or a tx
hash answering a signature request could satisfy the wrong pending action.

Attack (`RPCCorrelator.swift`, `RPCCorrelatorTests.swift`, `WalletBridge.swift`):
- Normal response accepted exactly once; duplicate ignored; late response after timeout ignored
  AND cannot resume a continuation twice (double-resume is a crash — prove it is impossible by
  construction, not just unlikely; look for the actual `CheckedContinuation` handling).
- Wrong topic, wrong chain (8453 vs anything else), id-less, id of a DIFFERENT pending request.
- A tx hash (`0x`+64 hex) arriving for `personal_sign`/`eth_signTypedData`, and a signature
  (`0x`+130 hex) arriving for `eth_sendTransaction` — rejected by expected method/shape, not only id.
- Disconnect, account change, session replacement while a request is pending → pending work must
  FAIL promptly, not hang and not succeed later.
- Two requests in flight (approval then swap) with responses arriving swapped: each must land on
  its own continuation.
- The on-chain receipt check in the swap flow must be independent of the bridge response: a forged
  "success" from the bridge must not mark the swap confirmed without a receipt.
